### `app/(app)/layout.tsx` — the auth gate

```tsx
export default function AppLayout({ children }) {
  return (
    <Suspense fallback={null}>
      <AuthedShell>{children}</AuthedShell>
    </Suspense>
  );
}
```

`AuthedShell` (same file) does the real work: calls `getAuthedUser()`, redirects to `/login` if unauthenticated; reads `x-pathname` from `headers()` (set by `proxy.ts`/`updateSession`); fetches `profile` and `getActiveWorkSession(user.id)` concurrently via `Promise.all`; redirects to `/onboarding` if there's no profile row yet or `onboarding_completed === false` (no profile row is treated as equivalent to "onboarding not done," since a fresh auth user has none until onboarding creates it). If authed and onboarded, it renders `AppShell`, passing `saveWeeklyGoal.bind(null, "deen")` and `saveWeeklyGoal.bind(null, "business")` as props — a live example of the RSC boundary rule below.

**Why `AuthedShell` is wrapped in its own `<Suspense>`.** A layout that reads runtime data via `headers()` forces the subtree dynamic, and per Next's own docs, that blocks navigation until the layout finishes rendering — the route's `loading.tsx` never gets a chance to show, which measured as a 413ms frozen old-screen in production after a cache purge. Wrapping the data-dependent part in its own boundary lets the boundary commit (old screen gone) the moment it suspends, not once it resolves.

Caveat, not a footnote: `redirect()` thrown from inside a Suspense boundary still works, but not identically to the old blocking layout. Once the shell has started streaming — which it now can, because `fallback={null}` lets it commit immediately — a `redirect()` thrown after that point can no longer be a real 307; the response is already underway, so Next falls back to a client-side redirect instead. Functionally equivalent here (nothing sensitive renders in that window) but a genuine behavioral difference, worth knowing if you're debugging a redirect that doesn't show up as an HTTP-level redirect in network logs.

This design does widen one real window: an onboarding-incomplete profile can very briefly start rendering an app route before the redirect fires. This is judged safe because every other `page.tsx` independently re-checks `getAuthedUser()` and redirects on its own (audited: 11 of 12 do — `/onboarding` is the one exception, and it renders only `<OnboardingWizard/>` with no user data and no DB read, so there's nothing to leak), and RLS sits under every table regardless. Net effect: a possible UX flash, not a security hole. If you touch this layout, don't casually "simplify" it back to a blocking layout — you'd reintroduce the 413ms freeze.

### Loading skeletons — `components/shell/route-skeleton.tsx`

Every route's `loading.tsx` is built from shared primitives here (`PageHeaderSkeleton`, `PanelSkeleton`, `KpiCardSkeleton`, `KpiStripSkeleton`, `DomainStatusStripSkeleton`, `WeeklyGoalsHeaderSkeleton`, `RowListSkeleton`), each deliberately mirroring the real component's own chrome (border, radius, padding) so the swap from skeleton to content doesn't shift layout.

The fade timing is not instant: `.route-skeleton-fade-in` (`app/globals.css`) applies a **130ms delay before a 160ms fade-in**. A route that resolves inside the delay window never paints a skeleton at all — only a genuinely slow one does. This exists specifically to avoid a flash-then-swap flicker on fast navigations (see `docs/superpowers/specs/2026-08-16-navigation-latency-fix.md` for the history — an earlier attempt removed `loading.tsx` sitewide and was reverted). Under `prefers-reduced-motion: reduce`, the 130ms anti-flicker delay is kept but the animation duration collapses to 1ms.

## Data layer — Supabase

Three client constructors under `lib/supabase/`, each for a distinct execution context:

- **`server.ts`** (`createClient`, async) — Server Components and Server Actions. Wraps `createServerClient` from `@supabase/ssr`; cookie writes are wrapped in try/catch because a Server Component can't set cookies (middleware refreshes the session instead).
- **`client.ts`** (`createClient`, sync) — Client Components. Thin wrapper over `createBrowserClient`.
- **`middleware.ts`** (`updateSession`) — called from root `proxy.ts`. Refreshes the session via `supabase.auth.getClaims()` and injects the `x-pathname` header the layout above relies on.

All three build the same typed client (`Database` from the generated `database.types.ts`) and throw explicitly if `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` are missing.

**Auth reads**, both in `lib/supabase/auth.ts`:

- `getAuthedUser` — wrapped in React's `cache()` (per-request memoization, not cross-request). Uses `supabase.auth.getClaims()` (local JWKS verification, ~1ms) rather than `getUser()` (~80ms network round trip) — a deliberate tradeoff, with the accepted cost being a revoked-but-not-yet-expired session isn't caught until the next refresh.
- `getProfile` — also `cache()`-wrapped, derives the user id from `getAuthedUser()` internally rather than accepting a `userId` param, so every call site is guaranteed to be asking about the current request's own user.
- `requireUser` — not cached; throws `"Not authenticated"` if unauthenticated, otherwise returns `{ supabase, userId }`. This is the pattern nearly every Server Action uses to get both a client and a verified user id in one call.

**RLS is the universal pattern, confirmed across the migrations directory**, e.g. (`supabase/migrations/048_classes_entity_and_syllabus_storage.sql:35-40`):

```sql
alter table public.classes enable row level security;
create policy "classes_own_row"
  on public.classes for all
  using (user_id = (select auth.uid()))
  with check (user_id = (select auth.uid()));
```

**Convention for a new migration**, verified rather than assumed, with the one real exception on each point:

1. **RLS enabled** on every new user-owned table — universal, no exceptions found.
2. **Policy named `<table>_own_row`, single `for all` policy** — the dominant pattern from the middle of the migration history onward. It is *not* how the earliest surviving migration does it: `017_sunnah_logs.sql` predates the convention and uses four separate verbose policies (one per verb). Write new migrations the `_own_row` way; don't copy 017 as a template.
3. **`security invoker` on RPC functions** — the default in 10 of 11 functions checked. The one exception, `delete_class_assessment` (`048_...sql:161-165`), is `security definer` because it needs to delete from `tasks`, which the caller doesn't otherwise have write access to for that purpose — and it's not a silent bypass: ownership is re-checked explicitly inside the function body (`where id = p_assessment_id and user_id = v_user_id`). Treat `security definer` as something you justify in-file the same way, not something you reach for casually.
4. **Indexed `user_id`** — universal in the sampled tables (`create index <table>_user_id_idx on public.<table> (user_id)`), sometimes as part of a composite `(user_id, date)` index for date-range queries.

Postgres SQL in this repo is clean on the timezone front — an audit found zero occurrences of `current_date`/`now()::date` anywhere in `supabase/` or query code; every date the app writes is an explicit string computed in the app layer first. Keep it that way — see the timezone rule below.

## Server Actions

Convention: one general `actions.ts` per route directory under `app/`, plus domain-specific files named `<domain>-actions.ts` for a distinct sub-concern living in the same route (e.g. `app/(app)/work/` has `actions.ts`, `targets-actions.ts`, and `tasks-actions.ts` side by side). 24 such files exist across the app tree.

**The `revalidatePath` pattern**, from `app/(app)/work/tasks-actions.ts`:

```ts
"use server";
function revalidateCoop(): void {
  revalidatePath("/work");
  revalidatePath("/");
}

export async function addAgendaTask(targetId: string, title: string, deadline?: string) {
  const trimmed = title.trim();
  if (!trimmed) return;
  const { supabase } = await requireUser();
  const { error } = await supabase.from("coop_tasks").insert({ ... });
  if (error) throw error;
  revalidateCoop();
}
```

Every mutation in a given actions file shares one small `revalidateX()` helper, called at the end of every successful mutation — revalidating both the domain's own route and `/` (Home aggregates data from every domain, so almost every mutation needs to revalidate it too). `.eq("user_id", userId)` scoping is applied on top of RLS as a second layer, not a substitute for it.

**The optimistic-update pattern — `components/co-op/pipeline-context.tsx` is the canonical example.** Three parts, always together:

1. `useOptimistic(initialTasks, reduce)` — a pure reducer over a small tagged-union of actions (`setStatus`, `block`, `edit`, `remove`, `add`) holds a client-only optimistic copy of the list.
2. `useTransition()` wraps every handler: `dispatch(...)` to apply the optimistic change synchronously, then `await theServerAction(...)` for real.
3. The `await` is wrapped in try/catch — but the catch doesn't perform the revert. React's `useOptimistic` reverts to the last-committed state on its own the moment the transition's action throws; the try/catch exists only to stop that throw from propagating to the nearest error boundary, and to set a separate, display-only `error` string so the user sees *why* the card snapped back. Don't add manual revert logic here — it would be redundant with what React already does, and the file's own comment says exactly this.

An insert (`addTask`) uses the same shape with a synthetic client-side id (`optimistic-${crypto.randomUUID()}`) so the new card can render before the Server Action confirms and returns the real one.

## The RSC boundary rule

From `AGENTS.md`, verbatim, because it has bitten twice and is easy to reintroduce:

> **Never pass a function as a prop from a Server Component to a Client Component.** Hit twice during the 2026-08-15/16 structural refactor (`AreaChart`'s `yTickFormat` callback, `GoalCard`'s `onSave` closure) — both times `tsc --noEmit` and the full `vitest` suite passed clean, and the bug only surfaced live in the browser console ("Functions cannot be passed directly to Client Components"). jsdom-based unit tests don't enforce the RSC serialization boundary — this class of bug is invisible to every automated check except an actual `next dev`/`next build` render.

**The fix, every time:** if the value is a Server Action (`"use server"`), a bound reference survives — `someAction.bind(null, arg)`, never a wrapping arrow function. If it's a plain formatting/callback function, replace it with a plain serializable value the Client Component formats internally.

The correct pattern in the wild, `app/(app)/page.tsx:106-107`:

```tsx
<WeeklyGoalsHeader
  onSaveDeen={saveWeeklyGoal.bind(null, "deen")}
  onSaveBusiness={saveWeeklyGoal.bind(null, "business")}
  ...
/>
```

Same pattern recurs at `app/(app)/layout.tsx:68`, `app/(app)/calendar/page.tsx`, `app/(app)/business/page.tsx`, `app/(app)/fitness/page.tsx`. No lint rule enforces this — `eslint-plugin-react-server-components` was evaluated and rejected (self-described by its own author as "an experiment," unmaintained since May 2024, and its one rule doesn't check prop serializability anyway). When you touch a `page.tsx` that passes props into a Client Component, mentally check every prop that's a function: real bound Server Action, or closure? Verify by actually loading the page and checking the browser console — `tsc`/`vitest` will tell you nothing.

## The timezone rule

Also from `AGENTS.md`, hit three times in one night across three different layers — shipping code (`lib/prayer-times`), hand-written SQL, and a test fixture:

> **The rule:** a calendar date is a function of an instant *and* a timezone. Never `new Date()`, `getUTCDate()`, or `current_date` as a stand-in. Use `localDateString(now, timezone)`, and for day bounds use `resolveLocalTime(dateStr, "00:00", timezone)` — not `` `${dateStr}T00:00:00Z` ``, which treats an already-local date as a UTC boundary and pulls in the previous evening.

`lib/date-utils.ts` is the source of truth:

- `localDateString(now: Date, timezone: string): string` — returns `YYYY-MM-DD` for `now` as seen in the given IANA timezone.
- `resolveLocalTime(dateStr: string, timeStr: string, timezone: string): Date` — resolves a local `"HH:MM"` on `dateStr` in `timezone` to a real UTC instant.
- `getTimezoneOffsetMinutes(date: Date, timezone: string): number` — the DST-aware supporting helper both of the above build on.

**A nuance worth flagging precisely**: the fix for the shipped prayer-times bug is *not* inside `lib/prayer-times/calculate.ts` itself — that file still reads raw `date.getUTCFullYear()/getUTCMonth()/getUTCDate()` and is deliberately timezone-naive; it just trusts whatever UTC Y/M/D fields it's handed. The actual normalization point is one layer up, in `lib/prayer-times/windows.ts`, which builds the `date` it passes down so that its UTC fields already equal the correct *local* day:

```ts
// windows.ts
const todayAnchor = new Date(`${localDateString(date, timezone)}T00:00:00Z`);
```

`computePrayerWindows` (in `windows.ts`) is the **only** safe entry point. This isn't hypothetical: on 2026-08-31, `components/settings/location-settings.tsx` was found calling `calculatePrayerTimes` directly with a raw `date: new Date()`, bypassing `windows.ts` entirely — the Settings location preview had been showing tomorrow's prayer times every evening after ~19:00 local, for months, while the "fixed" module sat one layer above it, untouched. Fixed in the same session by anchoring to `localDateString` the same way `windows.ts` does. The generalizable lesson: **when you fix a bug class at a chokepoint, grep for callers who bypass the chokepoint** — that check is cheap and nobody ran it the first time. Watch for the inverse failure too: a function that normalizes internally will *re-localize* a pseudo-instant like `new Date(\`${dateStr}T00:00:00Z\`)` a day backward in any timezone behind UTC — if you're passing a date-derived anchor into such a function, make it a real local instant (noon local is safest, being maximally far from either midnight boundary).

Tests for anything date-related must pin the boundary, not just the happy path: the same local time either side of the UTC rollover (e.g. 18:59 and 19:01 CDT) must produce identical results, plus at least one timezone *east* of UTC, where the bug direction inverts.

Always run `npx playwright test` unfiltered, both projects, before a deploy — never a `-g`-scoped subset.

**The SEED account**: a dedicated test-fixture account (`SEED_USER_EMAIL`/`SEED_USER_PASSWORD` from `.env.local`), entirely distinct from Ayman's real account, run against a live (not mocked) Supabase database. Confirmed distinct in `e2e/helpers.ts` and multiple `docs/superpowers/specs/*.md` references. Two engineers have inverted SEED vs. the real account in one night before — check which one you're pointed at before writing or deleting anything through a test endpoint.

**Only the Lead runs Playwright.** All specs drive one SEED account against one live database and every run rewrites the same `storageState` file — this is a second shared mutable resource beyond the git index (see below), and running it concurrently has already produced corrupted `storageState` (two `auth.setup` processes racing to write the same file, producing invalid JSON that then fails every subsequent test with a misleading `SyntaxError`) and cross-run row collisions where one run deletes or asserts on rows another run is mid-test on. The rule: the Lead runs `npx playwright test`; nobody else, not filtered, not a single spec. `tsc` and `vitest` are pure and stay free for everyone.

## Build / deploy

Full detail lives in `docs/DEPLOYING.md`; the critical fact worth internalizing before touching deploy at all:

**`vercel deploy` ships the current working directory, not a specific git commit.** In a shared working tree with multiple agents editing concurrently, deploying in place risks shipping someone else's uncommitted, unreviewed, possibly half-finished work. If `git status --short` is empty, deploying in place is safe. If it isn't, the correct method is a **pinned worktree**: `git worktree add /tmp/deploy-<sha> <sha>` against the exact known-good commit, copy `.env.local` and `.vercel/project.json` into that worktree (both are gitignored, so a fresh worktree has neither), and deploy from there — then remove the worktree afterward. Skipping the `.vercel/project.json` copy step doesn't fail loudly: the Vercel CLI silently creates a brand-new project named after the temp directory and deploys there instead, and the resulting confusing missing-env-var build failure looks like an environment problem when it's actually a wrong-project problem. Verify `.vercel/project.json` says `"projectName":"tracking-app"` before trusting a deploy.

Also documented in `DEPLOYING.md`: deploy code before schema (code should tolerate both the pre- and post-migration shape briefly, since a code deploy running hours behind a migration has already been caught mid-flight against a dropped table), and check `git merge-base --is-ancestor <live-sha> <your-sha>` before deploying to avoid silently rolling back someone else's already-shipped work.

`scripts/` has no dedicated deploy script — deploy is done by hand-following `DEPLOYING.md`'s CLI commands with a `VERCEL_TOKEN` from `.env.local` (the CLI's logged-in identity doesn't have visibility into this project's team scope, so token auth is required, not just `vercel login`).

## Multi-agent working conventions

Several agents share one working tree and therefore one git index. Both naive commit strategies race and have both caused real incidents in this repo:

```
git commit -m "msg" -- <paths>     # ignores the index; commits WORKING-TREE state,
                                    # so another agent's unsaved edit to a file you
                                    # own rides along silently.

git add <paths>; git commit        # reads the index at commit time; another agent
                                    # staging in the gap between your add and your
                                    # commit puts THEIR files in YOUR commit.
```

The second is strictly better but still unsafe — verifying with `git diff --cached` doesn't help, because the race happens *after* the verification. The index is shared mutable state; staging and committing has to be atomic with respect to every other agent, not just correct in isolation.

**The fix: `./scripts/agent-commit.sh "message" path/one path/two`, always.** What it actually does: takes an `mkdir`-based mutex (macOS has no `flock`, and `mkdir` is atomic on POSIX filesystems) with a 120-second timeout and a `trap ... EXIT` to guarantee release; once holding the lock, runs `git reset --quiet` to clear the index *only* (never touches the working tree, so nobody's uncommitted edits are ever at risk); stages exactly the given paths; prints `git diff --cached --stat` so you see precisely what will be committed before it happens; commits; releases the lock on exit.

Forbidden in this shared tree, unconditionally: `git add -A`, `git commit -a`, `git stash`, `git reset --hard`, `git checkout --`, `git clean`. All of them touch the *working tree*, not just the index, which means they can destroy or overwrite another agent's in-progress, uncommitted work — this has already happened (an engineer lost six minutes of a layout-test run to another agent's half-finished topbar edit sitting in the same dirty tree). If a commit lands under the wrong agent's message anyway, leave it — the code is correct and present, and rewriting history in a tree others are actively committing to is worse than a misattributed diff.
